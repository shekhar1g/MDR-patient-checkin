App-Initiated Pre-Check-In, Live

The patient's app starts the check-in, packages what the practice needs, and either hands it over as a QR code at the desk or pushes it straight into the EHR before the visit. Every protocol artifact below is produced on this page as you go, with the code that made it. Nothing is a picture of a JSON file.

    STEP 1

    Identity verification at IAL2

    ID.me simulated

    Before anything can be shared with a hospital, the patient proves who they are once, at NIST IAL2, through a credential service provider. The app stores the result and reuses it for every pre-check-in. On this page the ID.me round trip is simulated; the record it produces is the real shape the app keeps.

    Where the standards stand. The HL7 Interoperable Digital Identity and Patient Matching IG v2.0.0 describes IAL levels but states that they are not currently in any code system or value set in that guide. So there is no published FHIR element to say "this patient was verified at IAL2." Step 6 shows how we carry it anyway, labeled as a proposal.

    STEP 3
    Intake on the phone, as a US Core QuestionnaireResponse
    US Core 9.0.0 (SDC)
    
  
    The visit type picks the form. The patient answers on their phone, and the answers become a QuestionnaireResponse that follows the US Core 9.0.0 profile, which inherits from SDC and therefore names the exact Questionnaire version being answered. The KTC bundle allows US Core resources, so the form rides inside the same package as the clinical records.

    STEP 5
    Access control: expiry on every link, a PIN where the spec allows one
    SHL STU1 flag rules
    
  
    Every SMART Health Link this app makes carries an expiry, which the KTC guide requires. A PIN is a different matter. The KTC guide says patient apps SHALL use the U flag (direct file, no manifest), and the SHL specification says U SHALL NOT be combined with P (passcode). So the QR pass shown at the desk cannot carry a PIN and stay conformant. The link the app pushes to the EHR is not governed by the KTC guide's QR rules, so it can use the base SHL manifest flow with a passcode, and the passcode travels inside the authenticated API call.

    STEP 6
    Package, attest, encrypt, link
    KTC PatientSharedBundle · App Attestation
    
  
    Four things happen in order and all four are real on this page. The app assembles a PatientSharedBundle (one Patient, the selected US Core and CARIN resources, the QuestionnaireResponse, a Provenance for the identity check, and a FHIR-Rendered PDF as a PatientSharedDocumentReference). It signs the KTC guide's App Attestation with an ES256 key and puts the JWS in Bundle.meta.extension. It encrypts the bundle with AES-256-GCM as a JWE (alg dir, enc A256GCM). It hosts the file at a 256-bit random path and builds the shlink:/ payload.

    On the identity claim. The KTC guide's own provenance signal is the App Attestation, which answers "did a recognized app produce this?" It does not carry an identity assurance level. We add a Provenance whose verifier agent carries an MDR-defined extension naming the level, the credential service provider and the time. The receiving EHR is free to ignore it. We would rather the group tell us where this belongs than invent a home for it alone.

    STEP 7
    Check-in pass: QR at the desk, or a PDF
    KTC primary workflow
    
  
    The QR is the KTC guide's primary workflow and always works. Staff scan it, the EHR fetches the file with a recipient parameter, decrypts it with the key from the link, and files it. The PDF is the same FHIR-Rendered document that is already inside the bundle, saved to the phone for a practice with no scanner and no integration.

    STEP 8
    Direct API push into the EHR
    Fills the gap the guide names
    
  
    The KTC guide defines how a receiver fetches and files a package. It says separately that "a fuller check-in protocol" is being worked on to carry request context and a more integrated handoff between the provider check-in experience and the patient app. This step is how our app does that today, for a practice whose EHR it is already integrated with. Everything standard is marked; the two things we had to define ourselves are marked too.
    
  
    

  
    8.1 Capability gate and token CapabilityStatement · SMART Backend Services
    
  
    The app reads the EHR's CapabilityStatement and looks for three things: a token endpoint in the SMART oauth-uris extension, create on DocumentReference, and the proposed $receive-shl operation. If the EHR advertises none of them, the app falls back to the QR. Then it authenticates as a backend service: grant_type=client_credentials with a JWT client assertion signed by the app's registered key (ES384 here), asking for system/DocumentReference.c.

    8.2 Dispatch $receive-shl or DocumentReference create
    
  
    Two ways to hand the link over. The proposed operation takes a Parameters resource with the link, the passcode and the appointment, so a PIN-protected link works. The standards-only path creates a DocumentReference whose attachment.url is the shlink:/ URI and whose context.related points at the Appointment. DocumentReference has no field for a passcode, which is exactly why the operation exists.
